# Technical Investigation Report: Semi-E2E Digital Twin Lineage

**Investigation date:** 2026-10-12
**Scope:** `test_semi_e2e_pipeline` and its PyTorch, weight, emulation, oracle-test, and NPU-test counterparts.
**Method:** Static repository audit plus inspection of the public DeepSeek-V4-Flash `inference/model.py`, `inference/kernel.py`, and `inference/convert.py` referenced by the repository. The public URLs use the mutable `main` revision; this report does not claim a pinned upstream commit or that the scripts/artifacts were executed as part of this audit.

## 1. Executive Summary

The repository has a traceable **partial digital twin**, not a PyTorch-backed full-model replica and not a semi-E2E NPU twin.

* The C++ harness in [semi_e2e_pipeline.hpp](./include/moe/emu/semi_e2e_pipeline.hpp) and [semi_e2e_pipeline.cpp](./src/emu/semi_e2e_pipeline.cpp) connects real checkpoint weights through an intentionally reduced layer order: layer 0 attention, layer 2 attention/compressor/indexer side paths, then layer 1 MoE. It is expressly “semi” and reports stage fidelity.
* The canonical model code is **not checked into this repository**. The local [run_pytorch_layer_ref.py](./scripts/run_pytorch_layer_ref.py) is a standalone tensor-level PyTorch reimplementation/checker that cites DeepSeek-V4-Flash upstream. The upstream architecture and implementation references are identified in the code comments and corroborated against the public source, but their `main` branch is not version-pinned.
* The weights are not quantized or synthesized by the local fetcher. [download_dsv4_semi_e2e_weights.sh](./scripts/download_dsv4_semi_e2e_weights.sh) and [dsv4_fetch_tensors.py](./scripts/dsv4_fetch_tensors.py) range-fetch selected, already-serialized checkpoint tensors and repack their original bytes into a compact safetensors file. They also record routing metadata.
* There is **no Python script in the repository that creates `golden_semi_e2e_ref.bin`**. The file is generated by the host C++ [dsv4_semi_e2e_bench.cpp](./apps/dsv4_semi_e2e_bench.cpp) from real weights plus deterministic synthetic inputs. Python subsequently validates the v3 dump against independently computed PyTorch outputs. `verify_mxfp4_packing.py` separately audits nibble order.
* `test_semi_e2e_pipeline` combines algebraic/micro-tests with an optional real-weight pipeline run. The optional pipeline section returns after printing `SKIP` when weights are absent; it is not a full-model golden comparison.
* Target A, [test_custom_kernels_emu.cpp](./tests/emu/test_custom_kernels_emu.cpp), validates individual operator contracts and a host simulation of the indexer selection network. Target B, [npu_custom_kernels_device.cpp](./tests/npu/npu_custom_kernels_device.cpp), executes five arch35 operators on hardware against generated-in-memory CPU references. Neither target runs the semi-E2E pipeline end to end on an NPU.

**Verdict:** artifact extraction and per-layer parity are unusually well documented and include source-byte auditing; the precise lineage boundary is also explicit in the code. The strongest gap is architectural: the full upstream model is external, the parity script intentionally reproduces only a reduced/assumption-marked schedule, and the NPU suite is operator-level rather than pipeline-level. No NPU behavior or locally regenerated dump is asserted by this static investigation.

### 2.2 Mathematical contracts represented by the twin

Let `D=4096`, `HC=4`, `N=256` routed experts, top-k `K=6`, and the routed scaling factor be `1.5` for the tested model configuration.

| Stage | Mathematical contract and relevant distinctions |
|---|---|
| FP8 block-scaled linear/GEMV | For weight coordinate `(r,c)`, `W[r,c] = decode_E4M3(w[r,c]) * decode_E8M0(s[floor(r/128), floor(c/128)])`; output is `W @ x`. The checkpoint scale grid is per 128×128 block. The PyTorch model's quantized `Linear` dispatch quantizes activations and uses FP8 GEMM. The local parity helper instead dequantizes rows/blocks and applies `F.linear` in FP32; this is not bitwise reproduction of quantized activation GEMM. |
| MXFP4 group-scaled linear/GEMV | Each byte carries two E2M1 values in **low-then-high** logical column order. E2M1 magnitudes are `{0, .5, 1, 1.5, 2, 3, 4, 6}` with the high bit as sign; all 16 codes are finite. Multiply each value by the E8M0 scale for its row and 32-logical-element group, then compute `W @ x`. Typical routed expert logical `w1` shape is `[2048,4096]`, stored packed shape `[2048,2048]`, scale shape `[2048,128]`. |
| RMSNorm | `y = x * rsqrt(mean(x²) + eps)`, then multiply elementwise by learned gain when present. The local contract uses `eps=1e-6`; weightless normalization is used for per-head query normalization. The official module computes in FP32 and converts back to input dtype. |
| mHC / Sinkhorn | For the four-stream bundle `x`, flatten to `HC*D`; project with the `24×16384` `hc_*_fn`, scale by `rsqrt(mean(x²)+eps)`, then split the 24 mixes into four pre-gates, four post-gates, and a 4×4 combination matrix. Pre gate: `sigmoid(mix_pre*alpha[0]+base_pre)+eps`; post: `2*sigmoid(mix_post*alpha[1]+base_post)`. Combination logits use `alpha[2]`/base, softmax, epsilon stabilization, and a fixed 20 Sinkhorn-Knopp iterations. The C++ fold-back is `y[j,:] = post[j]*h_out[:] + Σ_i B[i,j]*x[i,:]`, followed by BF16 storage. This is a truncated iteration contract: with actual checkpoint weights the resulting row sums need not be exactly one after 20 iterations. |
| Shared-KV sliding-window attention | `wq_a:4096→1024`, learned `q_norm`, `wq_b:1024→64×512`, per-head weightless RMSNorm, and RoPE on the final 64 lanes. A single shared `wkv:4096→512` projection is normalized and RoPE-transformed per token. Each of 64 query heads scores the same 512-wide cache row: `logit[h,t]=(q[h]·kv[t])/sqrt(512)`. A learned per-head sink logit contributes to the softmax denominator but has no value-vector contribution, so real-token probabilities sum to at most one. The `SharedKvWindowCache` is a 128-row ring; append at position `p` overwrites `p mod 128`. |
| Hash routing | Compute FP32 gate logits `g = gate_weight @ x`; score `s_i = sqrt(softplus(g_i))`. For hash layers, expert indices are exactly `tid2eid[token_id]`; logits do not select membership. Gather the six selected scores, normalize their sum, then apply routed scaling to the routed contribution. The test's fixture row for token 3 is `[30,205,192,177,242,102]`. |
| Score routing (`noaux_tc`) | For non-hash layers, selection is `topk(s_i + bias_i)`, while returned routing weights are gathered from the **unshifted** `s_i`, normalized, and then route-scaled. The code keeps this separate from the hash path. `SqrtSoftplus(x)` is `sqrt(log1p(exp(x)))` up to softplus threshold 20 and `sqrt(x)` above that threshold (the threshold branch prevents exponential overflow). |
| SwiGLU | `gate=w1@x`, `up=w3@x`; `gate=clamp(gate, max=10)` (no lower clamp); `up=clamp(up,-10,10)`; `hidden=silu(gate)*up`; `expert_out=w2@hidden`. The routed experts use MXFP4; the shared expert uses FP8 in this slice. The MoE result is `1.5 * Σ_i route_weight_i * expert_i + shared_expert`, then BF16 before mHC fold-back. |
| Compressor C4A | Layer 2 uses ratio 4, head dimension 512, and `coff=2` overlap state. Project hidden inputs to KV and gate; add learned `ape`, softmax gates along the ratio/time axis, weighted-sum KV, RMSNorm, and compressor RoPE with `theta=160000`. The tested four-step cadence emits one token. In the benchmark's first-group fixture, overlap gate entries are `-inf` and the current half contributes. |
| Lightning indexer | Upstream computes a rotated/quantized query, compressed key cache, and per-head score `relu(q·k) * head_weight`, sums across heads, masks unavailable future compressed tokens, and selects top-k. In the semi-E2E benchmark, the head projection is real but historical FP8 query/key activation bytes and their scale inputs are synthetic because the needed history is not generated by this short slice. Do not equate its selected indices with an end-to-end model indexer result. |

The public upstream sources currently expose these forward signatures: `Attention.forward(self, x, start_pos)`, `Compressor.forward(self, x, start_pos)`, `Indexer.forward(self, x, qr, start_pos, offset)`, `Gate.forward(self, x, input_ids=None)`, `Expert.forward(self, x, weights=None)`, `MoE.forward(self, x, input_ids)`, and `Block.forward(self, x, start_pos, input_ids)`. Their implementations may change on upstream `main`; a reproducible archival investigation should record the exact upstream revision before treating these signatures as immutable.

### 2.3 The local PyTorch checker is intentionally not full parity

`run_pytorch_layer_ref.py` runs the order **attention layer 0 → attention layer 2 → MoE layer 1**. In its default mode it reads the exact `x_input` synthetic bundle from the C++ golden and reconstructs selected intermediates. Differences from the complete upstream model and from a complete C++ decode include:

1. It does not instantiate and call upstream `Transformer`/`Block`; it manually composes functional equivalents (`mhc_pre`, `attention`, `expert`, etc.).
2. Its parity attention uses a reused KV activation at eight warm-up positions and measures the next position, while the official `--attention-formula official` mode uses a one-token, `start_pos=0` attention convention. The `official` formula mode requires `--input source-embedding`; it is not compared to the synthetic-input golden.
3. It omits compressed keys from layer-2 attention in the parity schedule. It computes the compressor token separately and compares that output.
4. The benchmark creates synthetic indexer Q/K bytes and synthetic historical indexer cache/scale values, so there is no PyTorch indexer parity assertion against real historical model activations in this harness.
5. Dense FP8 and MXFP4 weights are dequantized for FP32 `F.linear`; this differs from the upstream activation-quantized FP8/FP4 GEMM path.
6. The C++ `SemiE2ePipeline::Run()` includes stage labels and assumptions for these substitutions. Treat `Fidelity::kReferenceWithAssumption` and `Fidelity::kSyntheticInput` as actual coverage boundaries, not generic “reference” labels.

## 3. Golden Dump & Weight Generation Infrastructure

### 3.1 Weight acquisition and compact safetensors creation

| File | Role |
|---|---|
| [download_dsv4_semi_e2e_weights.sh](./scripts/download_dsv4_semi_e2e_weights.sh) | Shell entry point. Fetches `config.json` and `model.safetensors.index.json` from `deepseek-ai/DeepSeek-V4-Flash` unless already present; invokes the Python range fetcher. |
| [dsv4_fetch_tensors.py](./scripts/dsv4_fetch_tensors.py) | Reads the index/config, selects tensors, uses HTTP byte ranges against the HF shards, and writes a new valid safetensors header with compact offsets. No PyTorch dependency. |
| [safetensors_view.hpp](./include/moe/emu/safetensors_view.hpp) | C++ mmap/header view of the repacked file used by the emulation pipeline. |
| [verify_mxfp4_packing.py](./scripts/verify_mxfp4_packing.py) | Checks the routed-expert MXFP4 payload dtype/shape and proves low-nibble-first decoding matches DeepSeek's `convert.py`, including a nonuniform GEMV probe. It does not generate weights. |

The shell defaults are:

* Repository: `deepseek-ai/DeepSeek-V4-Flash`, URL base `https://huggingface.co/deepseek-ai/DeepSeek-V4-Flash/resolve/main`.
* Output directory: `${DSV4_DATA_DIR:-<repo>/data/dsv4_layer0}`. CLI `--dir` overrides the directory.
* Attention layers `0,2`; MoE layer `1`; token ID `3`; maximum experts `8`; normal run downloads, `--dry-run` reports tensor plan/size only.
* The index/config are fetched once if missing. The script requires `curl` and `python3`; the fetcher uses Python standard-library modules. Large file ranges are downloaded separately rather than downloading whole model shards.
* The checked-in README records the expected default result as approximately **101 tensors / 365 MB**. The count/size depend on the current remote checkpoint index and should be re-measured, not treated as a content hash.

The selected MoE layer is a hash layer (`num_hash_layers=3`). The fetcher reads `layers.1.ffn.gate.tid2eid[token_id]`, then fetches the experts in that row, in rank order and up to `--max-experts`. Thus changing `--token-id` changes the required expert tensors and metadata. `--max-experts` is a cap; config `num_experts_per_tok` is the routing row width.

The generated safetensors metadata keys are:

| Key | Meaning |
|---|---|
| `produced_by` | `scripts/dsv4_fetch_tensors.py` |
| `source_repo` | Source model repo name |
| `attn_layers` | Comma-separated selected attention layers |
| `moe_layer` | Selected MoE layer |
| `moe_is_hash_layer` | Whether this layer uses `tid2eid` |
| `token_id` | Token whose route row determined which experts were included |
| `routed_experts` | Comma-separated original row entries |
| `num_experts_per_tok` | Configured route count |
| `vocab_size` | Configured token-table size |

The source tensor dtype/shape and payload bytes are copied from the source shards. Repacking creates contiguous compact `data_offsets`; it does **not** quantize, reinterpret, or regenerate model weights. Routed FP4 payloads can be labeled `I8` in safetensors even though their nibbles encode E2M1; the config and corresponding scale geometry supply the semantic interpretation.

### 3.2 Who writes the activation golden

The generator is the host executable [dsv4_semi_e2e_bench.cpp](./apps/dsv4_semi_e2e_bench.cpp), not a Python script. It reads:

* `data/dsv4_layer0/config.json`
* `data/dsv4_layer0/dsv4_semi_e2e.safetensors`

and normally writes `data/dsv4_layer0/golden_semi_e2e_ref.bin`. `--no-dump` disables writing. The semi-E2E test itself does not create the file. The Python checker requires a v3 dump; it cannot bootstrap one.

The v3 binary begins with a 48-byte little-endian header: magic `DSV4SE2E`, version `3`, dtype code `1` (BF16), stream count `4`, hidden size `4096`, token ID `3` for the default run, routed count `6`, Sinkhorn order `4`, compressed-token count, and indexer top-k. Its payload order is:

1. `x_final` BF16 `[4,4096]`
2. layer-0 and layer-2 combination matrices `B0`, `B2`, FP32 `[4,4]`
3. selected expert IDs INT32 `[6]` and routing weights FP32 `[6]`
4. `x_input`, `x_after0`, `x_after2`, BF16 `[4,4096]` each
5. `h_in0`, `h_in2`, `h_in_moe`, FP32 `[4096]` each
6. MoE `Bmoe`, FP32 `[4,4]`
7. six expert outputs, FP32 `[6,4096]`, in the serialized routing order
8. routed and shared expert sums, FP32 `[4096]` each
9. layer-2 emitted compressed token(s), BF16 `[compressed_count,512]`

The v3 fixture is a C++ emulation fixture, not a pre-baked device output. Its existence on a developer machine depends on running the host benchmark; it is intentionally not checked into source control (the README states there is no `data/` fixture transfer requirement).

### 3.3 Deterministic input and test parameters

| Input or setting | Value / derivation |
|---|---|
| Token ID | Default `3`; must match safetensors metadata. `Run()` rejects a mismatch so it cannot select experts that were not fetched. |
| Initial stream bundle | `std::mt19937(uint32_t(0x9E3779B9u ^ token_id))`, normal distribution mean `0`, stddev `0.02` (`initializer_range`), generated once at hidden width and broadcast into all four streams after BF16 conversion. |
| Indexer synthetic activation payload | `std::mt19937(0xC0FFEEu ^ uint32_t(token_id))`; E4M3 query/key bytes encoded from uniform `[-2,2]`; synthetic key scales use `0.5 + uniform(-2,2)*0.1`. |
| Default benchmark options | `decode_steps=4`, `indexer_seq_len=2048`, `warmup_window_tokens=8`, memory budget 4096 MB, time budget 1500 ms. |
| `test_semi_e2e_pipeline` real-weight case | Explicitly sets `decode_steps=4`, `indexer_seq_len=512`, `warmup_window_tokens=4`; artifact directory is `DSV4_SEMI_E2E_DIR` or defaults to `data/dsv4_layer0`. |
| `run_pytorch_layer_ref.py` parity defaults | `--input golden-synthetic`, `--attention-formula golden`, fixed token 3 and expected experts `[30,205,192,177,242,102]`, `torch.set_num_threads(4)`, v3 golden required; parity verdict threshold is cosine ≥ `0.9995`. |
| `test_semi_e2e_pipeline` micro-test RNG | Shared `std::mt19937` default seed `0x5EED` in [emu_test_support.hpp](./tests/emu/emu_test_support.hpp). The helper's fixed seed makes reruns deterministic; that suite does not print the seed at startup. |

The artifact fetch is deterministic only with respect to a fixed source checkpoint/revision, arguments, and server responses; the script uses the mutable HF `main` URL and does not pin a revision. For durable reproduction, first capture a specific model revision and its config/index (or update the fetcher to accept a revision), then record their hashes. The Python parity script can verify every cached tensor's source shard byte range with `--verify-source-offsets`; this audits extraction integrity but does not pin future runs to the same source revision.

### 3.4 Reproduction commands

Commands below reflect the checked-in interfaces. The shell downloader is Bash-oriented; on the Windows workstation use WSL. The host build and the PyTorch checker run without an NPU.

```bash
# From the repository root in WSL/Linux: acquire config/index and 101-ish tensors.
scripts/download_dsv4_semi_e2e_weights.sh

# Optional: redirect artifacts; alternatively use --dir DIR.
DSV4_DATA_DIR=/mnt/big/dsv4 scripts/download_dsv4_semi_e2e_weights.sh

# Preview selection/estimated payload without assembling the compact file.
scripts/download_dsv4_semi_e2e_weights.sh --dry-run

# Configure/build the host-only benchmark and tests.
cmake -S . -B build_emu -DENABLE_HOST_EMU=ON -DCMAKE_BUILD_TYPE=Release
cmake --build build_emu --target dsv4_semi_e2e_bench test_semi_e2e_pipeline test_custom_kernels_emu -j

# Write/update the v3 C++ golden; specify data dir if not using the default.
./build_emu/apps/dsv4_semi_e2e_bench --memory-budget-mb 2500
# Or: ./build_emu/apps/dsv4_semi_e2e_bench --data-dir /path/to/dsv4 --no-dump

# Optional independent packing/source checks, then PyTorch comparisons.
python3 scripts/verify_mxfp4_packing.py
python3 scripts/run_pytorch_layer_ref.py --source-only
python3 scripts/run_pytorch_layer_ref.py --verify-source-offsets
python3 scripts/run_pytorch_layer_ref.py
python3 scripts/run_pytorch_layer_ref.py --input source-embedding --attention-formula official

# Focused host suites.
ctest --test-dir build_emu -R 'test_semi_e2e_pipeline|test_custom_kernels_emu' --output-on-failure
```

The PyTorch commands need CPU PyTorch and `safetensors`. `--source-only` validates cache offsets/metadata and, in source-only mode, downloads/hash-compares source ranges without opening the binary golden or tensors as model weights. The `source-embedding` option downloads only the requested BF16 embedding row (token 3 by default) instead of loading the synthetic golden input; it prints norms and does not claim numerical parity against that synthetic golden.

**Legend:** “Exact / aligned” means the same operator math or data contract is tested; it does not imply bitwise equality or full model coverage. “Partial” marks a known schedule/precision/substitution boundary. “None” means the named suite does not exercise that item.

### 4.1 What is covered one-to-one, and what is not

* **Strong per-operator alignment:** mHC pre/post, compressor, indexer selection, and MXFP4 GEMV each have CPU oracle/device comparisons at the primitive/operator boundary. The target B suite is explicitly limited to the five arch35 operators and builds its oracle during the run; it does not consume `golden_semi_e2e_ref.bin`.
* **Strong host math/shape checks:** `test_semi_e2e_pipeline` has explicit tests for E2M1 decode, the two distinct FP8/MXFP4 scale index geometries, RMSNorm, cache eviction, hash routing, score routing, and asymmetric SwiGLU behavior. These tests isolate contracts instead of being an NPU run.
* **Partial pipeline parity:** the C++ pipeline and local PyTorch script agree on layer order, token-specific expert IDs, major serialized stage tensors, and selected quantization metadata. However, their FP32 dequantized linear path is a mathematical reference, not a reproduction of the upstream quantized activation kernels; layer-2 historical indexer inputs are synthetic; compressed KV is not fed into attention; and the attention convention is explicitly assumption-marked.
* **Not covered 1:1:** the complete upstream 43-layer forward pass, official full prefill/decode cache contents, a real embedding plus matching complete decoder state, and a full semi-E2E device launch chain. NPU operator success cannot be promoted to a claim that `test_semi_e2e_pipeline` has a device twin.

### 4.2 Test behavior and artifact-sensitive caveat

The real-weight section in `test_semi_e2e_pipeline` starts only if the expected safetensors path exists. If missing, it prints `SKIP` and returns from the section; the rest of its algebraic micro-tests still run. The test does not compare a pre-baked golden binary. As a result, a clean-checkout pass can mean “unit checks passed; assembled real-weight pipeline was not run.” Consumers should preserve that distinction in CI logs and reports.

In contrast, the NPU suite has an explicit device guard and the required `Physical Ascend NPU not detected` skip banner. Once a device is found, errors are failures. Its successful execution would establish device correctness for the covered primitive fixtures only—not the entire semi-E2E sequence.

## 5. Bridging the Current Gap to a True Semi-E2E NPU Twin

The minimum credible bridge is more than chaining the existing launch wrappers:

1. **Pin the reference inputs.** Record the upstream model revision, `config.json`, index file, fetched tensor byte hashes, token ID, and `tid2eid` route row. Do not depend on mutable `main` without recording the resolved revision.
2. **Define parity boundaries and fixture semantics.** Choose either the current explicitly reduced schedule or the true upstream decode behavior. Align warmup positions, position IDs/RoPE mode, compressor history, attention sink placement, compressed-key availability, and whether the input is synthetic or the actual embedding row. Remove “reference with assumption” only after the convention is settled.
3. **Implement missing device-side primitives or appropriate production calls.** The current five custom ops do not include the attention projections/FP8 GEMVs, RMSNorm, routing, score function, full SwiGLU expert composition, or the runtime/cache orchestration needed for this pipeline.
4. **Build a device pipeline runner with explicit stage I/O.** Use caller-owned device buffers and the project launch contracts; compare outputs after every stage against a CPU/PyTorch reference generated for the identical input and state. Include the real serialized expert order and verify selected expert tensors exist.
5. **Generate references on the test run, not from stale checked-in outputs.** Print the seed and configuration, retain enough exact inputs to reproduce failures, and test structural invariants as well as numerical parity (cosine, relative L2, finite values, Sinkhorn sums, cache/window state, compressor HOLD/EMIT, exact top-k indices).
6. **Keep verification gates separate.** Run the host oracle, BiSheng dav-3510 compile gate, NPU build/linkage gate, then the device run on actual hardware. Compilation/build verifies that the device path builds, not that the complete semi-E2E pipeline computes correctly.

Until those steps exist and a real hardware run is recorded, the accurate claim is: **the project has a host semi-E2E C++ emulation, a PyTorch parity checker for its reduced schedule, and on-device tests for five individual operators; it does not yet have a PyTorch-full-model-to-NPU semi-E2E digital twin.**
